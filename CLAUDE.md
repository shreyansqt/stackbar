# CLAUDE.md — StackBar

Native macOS menu bar app to run & monitor local dev services, plus a TypeScript
CLI + MCP server. Read this before working in the repo.

## Build & run

- **Project is generated by XcodeGen** from `project.yml` — `StackBar.xcodeproj` is
  gitignored. After editing `project.yml` or adding/removing a source file, run
  `xcodegen generate`.
- Build from CLI (no signing needed for local):
  ```sh
  xcodegen generate
  xcodebuild -project StackBar.xcodeproj -scheme StackBar -configuration Debug \
    -derivedDataPath ./build build CODE_SIGNING_ALLOWED=NO
  open build/Build/Products/Debug/StackBar.app
  ```
- After changing Swift sources, you must rebuild **and relaunch** the app
  (`pkill -f StackBar.app` then `open …`) — a running instance won't hot-reload.
- TS tools: `cd tools && npm install && npm run build` (outputs to `tools/dist/`,
  gitignored). The MCP server registered with `claude mcp` points at
  `tools/dist/mcp.js`, so rebuild after editing `tools/src/`.
- **The MCP server is also bundled into the app** for distribution. The
  `Bundle MCP server` post-build phase (`Scripts/bundle-mcp.sh`) runs
  `npm run bundle:mcp` (esbuild → one self-contained `tools/dist/mcp.bundle.js`,
  deps inlined) and copies it to `StackBar.app/Contents/Resources/mcp/mcp.js`. So
  the DMG ships with MCP inside; colleagues register it via
  `claude mcp add stackbar -- node /Applications/StackBar.app/Contents/Resources/mcp/mcp.js`
  (no clone/build). The bundled file has no cwd assumptions — `client.ts`/`store.ts`
  resolve everything under `~/Library/Application Support/StackBar`.
- SourceKit in-editor diagnostics often show false "Cannot find type" errors
  (single-file analysis can't see the whole module). **Trust the xcodebuild
  result**, not those.

## Architecture (Sources/)

- `StackBarApp.swift` — `@main`; `AppDelegate` owns the `ServiceManager` and
  `MenuBarController`; terminates all services on quit. No SwiftUI window scenes
  (menu-bar-only); aux windows are opened natively via `WindowManager`.
- `ServiceManager.swift` — owns `runners`, the workspace folder list
  (`workspaces.json`), `rescan()` (discover + reconcile), 2s health timer, startup
  orphan cleanup, and starts the `ControlServer`. Forwards each runner's
  `objectWillChange` up so the menu refreshes on per-service status changes.
- `RunningService.swift` — one service's runtime: spawns each command in its own
  process group (`perl setpgrp`, tagged `STACKBAR_MANAGED`), captures logs
  (combined + per-command), tracks status + per-command status, runs stop commands
  **after** start processes exit, port-kill backstop (skips container runtimes).
- `WorkspaceScanner.swift` + `JSONC.swift` — discover `.stackbar.json` files
  (pruned recursive scan) and parse JSONC into `Service`s with a stable
  path-derived id.
- `Service.swift` — model (`commands`/`stopCommands`/`port`) + `ServiceStatus`
  (idle/starting/running/stopping/crashed).
- `MenuBarController.swift` — the `NSStatusItem` + `NSMenu` (rebuilt per open via
  `NSMenuDelegate`), the status-driven glyph (brightness/spinner/checkmark/triangle),
  and the sectioned service submenu.
- `ControlServer.swift` + `HTTP.swift` — localhost-only token-authed HTTP server
  (Network.framework, minimal hand-rolled HTTP). Endpoints: GET `/services`,
  POST `/rescan`, GET/POST `/workspaces`, POST `/services/<id>/{start,stop,restart}`,
  `/start-all`, `/stop-all`.
- `LogStore.swift` / `LogTextView.swift` / `LogWindowView.swift` — on-disk log
  files + the native `NSTextView` console (ANSI color, line numbers).
- `Log.swift` — StackBar's own diagnostic log (`stackbar.log`).

## Conventions & gotchas

- **Config is files, not in-app.** Services come from repo `.stackbar.json` files
  discovered by scanning workspace folders. There is no add/edit/remove-service UI
  or API anymore — only workspace add/remove + rescan. The CLI's `stackbar init`
  scaffolds a `.stackbar.json` (it writes the file directly, then rescans); it is
  not a service-registration API.
- **`@MainActor`**: `ServiceManager`/`RunningService`/`MenuBarController` are main-
  actor. Shell-scanning helpers used off the main thread (orphan cleanup,
  `killProcessOnPort`, `processName`) are `nonisolated` — keep them so.
- **Never block `init`/launch with process scans.** A synchronous full-pid `ps`
  scan once hung launch (control server never came up). Orphan cleanup runs async.
- **Don't kill container runtimes.** The port backstop must skip OrbStack/Docker/
  containerd (it proxies container ports) or stopping a docker service wedges the
  daemon. See `protectedProcessNames`.
- **macOS `ps` only exposes env per-pid** (`-p`), not in a full listing — that's why
  marker-based orphan cleanup pgreps candidates first, then checks each one's env.
- **NSMenu is a snapshot per open** — it can't live-update while open (so e.g.
  uptime is as-of open time).
- **Two service-data paths — keep them in sync.** `list_services` and all
  start/stop/rescan tools go through the running app's HTTP control server
  (`client.ts`). The log tools (`get_logs`/`search_logs`) resolve names *offline*
  via `store.ts`, which reads the `logs/<id>.meta.json` files the app writes
  per-service. There is **no** `services.json` registry — don't reintroduce a
  dependency on one. If logs reject a valid name while `list_services` works, the
  bug is in `store.ts`'s file-derived view, not name matching.

## Testing changes

Drive the running app via the CLI to verify behavior, e.g.:
```sh
node tools/dist/cli.js list
node tools/dist/cli.js start <svc>;  # watch status / logs
```
Read `~/Library/Application Support/StackBar/stackbar.log` to diagnose runtime
issues. When testing start/stop cycles for docker-backed services, watch that
OrbStack stays up (`docker ps`).
